\section{Implementation}

This chapter provides a comprehensive, technically rigorous examination of the implementation of the BkLib Online Library Management System. It articulates the layered system architecture, foundational technology stack, and engineering decisions powering the platform. Subsequently, it delivers a detailed module-by-module breakdown across four core operational subsystems: Authentication and Access Governance, Reader Self-Service, Librarian Circulation and Operational Administration, and Platform Governance and System Infrastructure. Each module is documented through both user interface interaction workflows and core technical implementations, supported by production code snippets, database schemas, and background job algorithms.

\subsection{Technology Stack and Architectural Infrastructure}

The BkLib platform is architected as a decoupled, multi-tier system composed of three primary software tiers: a client Single-Page Application (SPA) built with React and Vite, a core API Gateway and Business Logic service implemented in Node.js/Express with Prisma ORM, and a dedicated AI Microservice powered by Python, FastAPI, Google Gemini, and ChromaDB.

\subsubsection{Front-end Presentation Layer: React.js and Vite}
The front-end user experience is implemented as a modern Single-Page Application (SPA) using React.js 18 paired with the Vite build toolchain. Vite delivers instantaneous Hot Module Replacement (HMR) and highly optimized ES module bundling for production deployment. The presentation layer employs declarative component hierarchies, React Router DOM for client-side role-guarded routing, and Axios interceptors for automated JWT injection and token refresh. On the client side, components manage optimistic UI updates, debounced catalog search inputs, multi-channel notification bells, real-time circulation status indicators, and an embedded floating AI assistant widget with streaming responses.

\subsubsection{Back-end Core Server: Node.js and Express}
The core application server is constructed upon Node.js and the Express framework using TypeScript. It functions as the central API gateway and orchestrator for business logic, catalog management, circulation rules, user accounts, and session administration. The server enforces a modular, layered software architecture comprising Controllers, Services, Middlewares, and Background Cron Jobs. It delegates AI inference tasks (RAG context querying, document embedding generation, personalized recommendations) to the dedicated Python AI service via secure internal HTTP endpoints authenticated through shared secret tokens (\texttt{X-Internal-Key}).

\subsubsection{Dedicated AI Microservice: Python and FastAPI}
AI capabilities are isolated into a standalone microservice developed in Python 3.10+ using FastAPI and Pydantic v2. This service harnesses high-throughput asynchronous execution to deliver low-latency NLP endpoints. Its key responsibilities include generating vector embeddings via pre-trained Transformer models, executing semantic book search with cosine similarity, coordinating Retrieval-Augmented Generation (RAG) over library regulations and FAQ repositories, and driving function-calling tools that bridge patron inquiries with live database records.

\subsubsection{Data Modeling and ORM: Prisma}
Prisma ORM is leveraged as the data abstraction and query engine within the Node.js service. Prisma provides end-to-end type safety across the application code and database layer, automatically generating TypeScript definitions from the declarative schema (\texttt{schema.prisma}). It manages automated schema migrations, relation modeling, and complex transactional queries across loans, fines, hold queues, and audit logs while guaranteeing ACID transaction semantics for critical operations like checkout and return.

\subsubsection{Relational Database: PostgreSQL}
PostgreSQL serves as the primary relational data store for all persistent business entities, including patron identities, physical inventory items, circulation ledgers, system configurations, and security audit trails. PostgreSQL guarantees strict ACID compliance for loan and fine settlement transactions, leverages B-Tree indexes for rapid metadata queries, and utilizes JSONB columns to capture before-and-after audit diffs and dynamic system parameters without requiring table migrations.

\subsubsection{Vector Store and Embedding Infrastructure: ChromaDB and Multilingual Models}
Text embedding representations for library documents, summaries, and FAQ knowledge bases are managed through a dual-vector architecture:
\begin{itemize}
    \item \textbf{In-Memory Vector Database (ChromaDB):} Serves as the high-speed vector retrieval engine for the library's official rules and FAQ documentation. The FAQ corpus is partitioned into overlapping chunks (400 characters, 60-character overlap) and indexed into ChromaDB collections during application startup.
    \item \textbf{High-Dimensional Embeddings:} Generated via \texttt{SentenceTransformer} utilizing the \texttt{paraphrase-multilingual-MiniLM-L12-v2} model (384-dimensional dense vectors) or Google Gemini's \texttt{models/text-embedding-004} (768-dimensional dense vectors). This enables bilingual semantic matching across Vietnamese and English bibliographic records.
\end{itemize}

\subsubsection{Adaptive Hybrid Search Strategy}
To overcome the limitations of pure keyword search (which fails on synonyms and conceptual phrasing) and pure vector search (which can miss exact ISBNs, call numbers, or proper nouns), BkLib implements an \textbf{Adaptive Hybrid Search Engine}. The engine computes a unified composite score:
\begin{equation}
    S_{\text{hybrid}} = w_{\text{semantic}} \cdot S_{\text{cosine}} + w_{\text{keyword}} \cdot S_{\text{overlap}}
\end{equation}
The weights $w_{\text{semantic}}$ and $w_{\text{keyword}}$ dynamically adjust according to query token count:
\begin{itemize}
    \item \textbf{Short Queries ($<3$ tokens):} $w_{\text{semantic}} = 0.40, w_{\text{keyword}} = 0.60$ (prioritizing exact title/author matching).
    \item \textbf{Medium Queries ($3-5$ tokens):} $w_{\text{semantic}} = 0.65, w_{\text{keyword}} = 0.35$ (balanced conceptual and keyword weighting).
    \item \textbf{Long Queries ($>5$ tokens):} $w_{\text{semantic}} = 0.80, w_{\text{keyword}} = 0.20$ (heavily favoring semantic intent).
\end{itemize}

\subsubsection{Security, Authentication, and Role-Based Access Control}
System security is established on four pillars:
\begin{itemize}
    \item \textbf{Stateless JWT Sessions:} Access tokens are signed using HMAC-SHA256 with short lifespans (15 minutes), supplemented by refresh tokens stored in HTTP-only cookies or secure headers for session persistence.
    \item \textbf{Bcrypt Hashing:} Passwords undergo salted Bcrypt hashing with configurable rounds (\texttt{BCRYPT\_ROUNDS = 10}).
    \item \textbf{Brute-Force Account Lockout:} Accounts incurring five consecutive failed authentication attempts are automatically locked for fifteen minutes (\texttt{lockedUntil}).
    \item \textbf{Granular RBAC:} Enforces role barriers across three hierarchical roles: \texttt{READER}, \texttt{LIBRARIAN}, and \texttt{ADMIN}.
\end{itemize}

\subsubsection{External Integrations: Open Library, Google Books, and Nodemailer}
\begin{itemize}
    \item \textbf{Bibliographic APIs (Google Books, Open Library, IT Bookstore):} Automated fallback cascade that enriches catalog records with cover images, publishers, publication years, and descriptions upon ISBN entry.
    \item \textbf{Transactional Messaging (Nodemailer):} SMTP integration delivering HTML emails for 6-digit OTP verification, loan approvals, pickup readiness notices, and due date alerts.
\end{itemize}

\subsubsection{Background Task Processing: node-cron}
Automated platform maintenance is governed by scheduled cron jobs via \texttt{node-cron}. Specifically, a daily sweep executed at 01:00 AM evaluates all reservations in \texttt{READY\_FOR\_PICKUP} status whose three-day grace period has lapsed, automatically marking them as \texttt{EXPIRED}, freeing physical copies, and advancing the queue to the next waiting patron.

\subsubsection{User Interface Implementation}

\paragraph{Login Page}
The primary entry portal provides unified authentication with role-switching tabs.

    \centering
    \includegraphics[width=0.92\linewidth]{Images/Auth_DangNhap.png}
    \vspace{15pt}
    \caption{BkLib Login Interface with Dual-Role Selector Tabs}
    \label{fig:auth_login}

\textbf{Layout \& Functionality:} The page uses a two-column composition: a library-themed visual panel introduces the service, while the form panel contains the BkLib identity, role selector, credential fields, and account-support actions. The role selector separates the reader entry point from the staff entry point. Although the identifier field is labelled ``Email hoặc Tên đăng nhập'', the current authentication service resolves accounts by email; the form therefore submits the value as an email address. Client-side checks reject an empty email, a malformed email address, or an empty password before the request is sent. The password visibility control changes only how the value is displayed. The ``Ghi nhớ đăng nhập'' checkbox is currently a visual preference and does not change token persistence: the authentication context stores the access token, refresh token, and user profile in local storage after every successful login. After authentication, the selected role tab is checked against the returned account role and the user is routed to the matching reader, librarian, or administrator workspace. A role-tab mismatch is reported in the form rather than silently opening a different workspace.

\paragraph{Registration Page}
Self-service onboarding form for new library members.

\textbf{Layout \& Functionality:} The registration form collects full name, email, optional phone number, optional student ID, a required home branch, password, password confirmation, and agreement to the displayed terms. The interface then navigates to the OTP page with the registered email and registration purpose carried in route state. \textbf{Layout \& Functionality:} Password recovery is presented in a three-stage modal opened from the login page. In the first stage, the user supplies an email address and requests a reset code; the service returns the same general response whether or not the account exists, preventing the form from revealing account membership. For a registered address, a six-digit code is emailed and is valid for 15 minutes. In the second stage, the interface checks that six characters have been entered before allowing the user to continue; this is a client-side step only, and the server verifies the submitted code together with the email when the final reset request is made. In the third stage, the user enters and confirms a replacement password, then submits the email, code, and new password to the backend. A successful reset consumes the OTP and returns the user to the login flow; invalid or expired codes are presented as an error in the modal. The registration OTP screen is a separate route: it verifies the six-digit code against the server, and a valid registration code changes the account status to active. Registration codes expire after 10 minutes, whereas password-reset codes expire after 15 minutes.
\begin{itemize}
    \item \textbf{Step 1 (Request OTP):} The user enters an email address. The response deliberately does not disclose whether the address is registered; for an existing account, the backend issues a six-digit reset code with a 15-minute validity period and sends it by email.
    \item \textbf{Step 2 (Enter OTP):} The interface accepts a six-character code and advances to the password form. Actual code validation takes place on the server with the final reset request, not at this intermediate screen.
    \item \textbf{Step 3 (Set New Password):} The user enters and confirms the replacement password. The backend looks up an unused, unexpired reset code for that account, hashes the new password, updates the account, and marks that code as used.
\end{itemize}

\subsubsection{Technical Implementation Highlights}

\paragraph{Registration and Email Verification}
The authentication workflow is divided between the React form, the Express authentication routes, and the authentication service. The client performs immediate field-level checks to reduce avoidable requests, while the service enforces uniqueness for email and student ID, hashes the password using the configured bcrypt cost, assigns the default reader role, and creates the account in \texttt{PENDING\_VERIFICATION}. It then persists an OTP record containing its purpose, expiry, and unused state before requesting delivery through the mailer. OTP verification is scoped to the account, code, purpose, unused state, and expiry time. A successful registration verification consumes the code and activates the account. These persisted checks, rather than the presence of a six-character value in the browser, determine whether verification succeeds.

\paragraph{Login, Tokens, and Account Protection}
Login first resolves the account and role, then rejects accounts that are unverified, suspended, banned, or still within a temporary lock period. Password verification uses bcrypt comparison. Failed attempts are counted; the fifth consecutive failure starts a 15-minute lock and resets the counter, while a successful login clears the failure state and updates the last-login timestamp. The service issues a short-lived access token and a refresh token with separate signing secrets and expiry configuration. The frontend attaches the access token to API requests and attempts token refresh after an unauthorized response. Role enforcement is performed by the backend authentication and authorization middleware on protected routes; the login tabs provide an additional user-facing routing check, not the security boundary. Successful login is recorded in the audit log with request IP address and user-agent when available.

\paragraph{Password Recovery}
Password recovery uses a distinct \texttt{RESET\_PASSWORD} OTP purpose. The request endpoint uses a generic response for both existing and non-existing addresses. The reset endpoint verifies the email-code pair and expiry on the server, hashes the replacement password, updates the user record, and records the OTP as used. Unlike registration, the current password-reset endpoint does not enforce an eight-character minimum on the server; the recovery form checks that the two entered values match but does not enforce that minimum length either.

\subsection{Reader Module}

The Reader Module provides self-service capabilities for library patrons. It enables students and faculty to explore the library catalog, manage physical-item loans and reservations, review their circulation history, and consult an AI assistant.

Personalized operational hub rendered upon reader login.

\textbf{Layout \& Functionality:} The dashboard greets the signed-in reader and provides a direct route to catalog discovery. Four summary indicators show the number of active loans, overdue records, active reservations, and unpaid fines. A recent-loan area presents up to five current loans with title, author, cover, and due-date status, with links to the book record and the complete loan list. A separate recommendation strip loads independently from the summary data so that a slow recommendation response does not block the dashboard. Recommendation cards show the reason label, availability, and rating when these values exist; readers without borrowing history receive popular-title recommendations, while an empty or unavailable recommendation response produces a prompt to explore the catalog.

Multi-criteria discovery interface for library resources.

AI results may display a match score, a short relevance explanation, the search mode and confidence level, and suggested alternative queries when confidence is low. If the AI service is unavailable, the backend falls back to basic database keyword matching and returns a fallback indicator. The underlying preference model also stores channel-level options, but the current page does not expose every channel as a control. The profile route is shared with staff accounts, with role-specific navigation information shown alongside the common account settings.

\subsubsection{Technical Implementation Highlights}

\paragraph{Catalog Queries and Reader Search}
The ordinary catalog view is backed by the books API, which filters active records by title, author, ISBN, and optional category, then returns a bounded page with the book's key display fields and availability counts. The React page applies a 500-millisecond debounce to ordinary text search and requests another page when the reader changes pagination. AI search is a separate API path: the Express service calls the Python search endpoint and passes through result metadata such as search mode, confidence, fallback state, and suggested queries. If that service fails, Express performs a bounded keyword search against active book records. This separation keeps exact metadata lookup available independently from semantic ranking.

\paragraph{Circulation Self-Service}
Reader-facing loans, history, reservations, and fine summaries are assembled from the same persisted circulation records used by the staff workflows. A renewal request is validated against account status, ownership, loan status, unpaid fines, due date, configured renewal count and duration, and reservation pressure before the record is updated. Reservation creation similarly rejects inactive accounts, unpaid fines, overdue loans, exhausted borrowing limits, duplicate active requests, and titles already borrowed by the same reader. When a copy is available, the service assigns it and starts the pickup window; otherwise it appends the request to the queue. Cancellation re-indexes waiting positions and, when the cancelled request held a copy, either promotes the next waiting reader or releases that copy back into inventory.

\paragraph{Reader Reviews}
Review submission is validated by the backend, which checks reader eligibility, enforces the permitted rating range, and limits each reader to one review per book. After a review is created or updated, the system recalculates the book's average rating and review count from visible reviews so that the catalog displays current feedback statistics.

\paragraph{Conversational Assistant}
The chat widget sends the current question and recent conversation context to the Express streaming endpoint. Express obtains recent persisted turns, forwards the request to the Python service, and streams the returned server-sent-event chunks to the browser while accumulating the completed reply for chat history. The Python service retrieves up to three relevant FAQ/rule passages from the vector collection and places them in a constrained prompt for Gemini; when retrieval produces no relevant context, the prompt instructs the assistant to avoid inventing a policy answer. The implemented assistant is therefore a retrieval-augmented policy assistant, not a function-calling agent connected to personal circulation records.

\subsubsection{Technical Implementation Highlights}

\paragraph{Desk Transactions and Circulation Rules}
The circulation interface acts as an operator-facing client for the circulation service; the business rules remain in the service layer. A checkout verifies that the reader is active, has no pending fines, remains within the role-dependent borrowing limit, and is entitled to the scanned copy. The service creates an active loan with a due date derived from system configuration, changes the copy state, fulfills a matching reservation when applicable, adjusts the available-copy count, and records an audit event. On return, it locates the active loan by copy barcode, calculates overdue days using the configured holiday list, creates a pending fine when appropriate, closes the loan, and either allocates the copy to the next waiting reservation or returns it to the available pool. Fine settlement changes the fine status and records a separate audit event. These operations share the persisted records used by reader history and staff dashboards.

\paragraph{Catalog and Inventory Management}
Catalog operations maintain a book-level bibliographic record and separate physical-copy records. Book creation validates ISBN uniqueness, category existence, and referenced branches before creating the title and its requested branch allocations. Copies receive generated barcodes and begin in the available state. Editing can update bibliographic fields and branch-level inventory totals, while the copy editor supports specific copy attributes. Soft deletion protects active loans by rejecting removal while any copy remains on loan. Excel import is handled as a batch workflow, and ISBN enrichment is delegated through the backend's catalog service to the AI service's ISBN endpoint; returned fields are prefill suggestions and remain subject to staff review.

\paragraph{Reservation Queue and Expiry Management}
Reservations are maintained in a queue for each title. When a copy is available, a request is assigned that copy and marked ready for pickup; otherwise, it is added to the waiting queue with a position. Returns and cancellations can promote the earliest waiting request. The scheduled expiry job checks ready reservations daily, expires pickup windows that have elapsed, releases the reserved copy, and advances the queue. These reservation and copy-state changes determine the status displayed in the reader and librarian workflows.

\paragraph{Notifications and Operational Reports}
Broadcast requests select active recipients and optionally constrain them by role. Notification records are inserted in batches, after which the service attempts the requested external delivery. Email uses the configured mail transport (or a development test account when SMTP is not configured). SMS dispatch is simulated; no production SMS gateway is integrated. Dashboard trend series are built from persisted borrow and return timestamps for selectable date windows; top-title totals are aggregated from borrow records, while audit activities are ordered by creation time. The report page's download is a client-generated JSON snapshot of the currently loaded dashboard values, not a server-generated spreadsheet or a verified delivery report.

\subsubsection{Technical Implementation Highlights}

\paragraph{Role Governance and Account State}
The administrator user list requests records through a paginated, filtered endpoint, while the service caps page size and applies the selected role, status, and case-insensitive name/email search. Status and role mutations are validated against the target account and supported values. Self-locking and self-role-change are rejected to reduce the risk of administrative lockout. Successful changes retain the actor, target entity, old value, new value, and assigned risk level in the audit log. The frontend updates the affected row after a successful response and reports failures without treating a local state change as authoritative.

\paragraph{Dynamic Configuration}
Circulation policy values are stored in the system-configuration table and read by the circulation service when it needs loan duration, borrowing limits, fine rate, renewal allowance, renewal duration, or holiday dates. This allows policy changes to affect subsequent transactions without changing application code. The administrator form sends key/value pairs to an upsert operation; each saved key is audited with its prior and new value. The interface treats values as text, so the backend validation and the consuming service's parsing remain important parts of the configuration contract.

\paragraph{Branch Lifecycle}
Branch records associate users and physical copies with a library location. The administrator can create a branch, edit its contact and manager fields, or deactivate it. Deactivation is intentionally guarded by a reference check: a branch with assigned users or copies cannot be taken out of operation until those records have been reassigned. The data model stores an active flag, and active branches are returned to the management view. The synchronization label shown on a branch card is a presentation status and is not backed by a separate synchronization-monitoring service.

\paragraph{Audit Trail}
Audit records capture the actor when known, action, entity type and identifier, optional IP address and user agent, before-and-after JSON values, risk level, and timestamp. The backend query supports filters for actor, action, risk level, and date range and orders results newest-first. The administrator screen currently exposes action, selected date, and risk filters and shows the fields available in its table; it does not yet provide a JSON diff expansion. Audit data should therefore be understood as persisted accountability information, with only a subset surfaced in the current table.

\paragraph{Dashboard Aggregation and Backup Scope}
The dashboard service aggregates counts and fine totals from books, users, borrow records, and fines, then groups borrow and return timestamps into consecutive daily series. It also derives popular titles from borrow history and includes recent audit events. If the live database cannot provide dashboard data and a valid snapshot exists, the service can derive a limited fallback overview from that snapshot and labels the source accordingly. Manual snapshot creation serializes selected table records to a timestamped JSON file on the server and records the operation in the audit log. Restore uses a Prisma interactive transaction to upsert only system configurations and branches, then logs the critical restore event after the transaction. It is a targeted configuration recovery facility, not a complete database backup-and-restore mechanism or a point-in-time recovery system.

\subsection{Deployment Stage}

This section describes the deployment strategy and infrastructure setup for the project. The system is distributed across different cloud providers to leverage their specific strengths: Vercel for the frontend and Express backend due to its seamless CI/CD integration and serverless architecture, and Google Cloud Run for the AI service to handle containerized machine learning workloads efficiently.

\subsubsection{Frontend Deployment}
The frontend application, built with React and Vite, is deployed on Vercel. Vercel provides a global Edge Network that ensures fast content delivery and high availability. The deployment process is integrated directly with the GitHub repository. Upon every push to the main branch, Vercel automatically triggers a new build process, executing the production build script, and updates the live website. Environment variables, such as backend API URLs, are securely managed within the Vercel dashboard.

\subsubsection{Backend Deployment}
The backend service, built with Node.js and Express, is also deployed on Vercel, utilizing Serverless Functions. This approach eliminates the need for manual server provisioning and scales automatically based on incoming traffic.
To configure the deployment, a \texttt{vercel.json} file is utilized at the root of the backend directory to specify the build environment and routing rules. The configuration directs all incoming API requests to the main application entry point \texttt{src/app.ts}, utilizing the \texttt{@vercel/node} runtime:

\begin{verbatim}
{
  "version": 2,
  "builds": [
    {
      "src": "src/app.ts",
      "use": "@vercel/node"
    }
  ],
  "routes": [
    {
      "src": "/(.*)",
      "dest": "src/app.ts"
    }
  ]
}
\end{verbatim}
This setup allows Express routing to function seamlessly within a serverless environment.

\subsubsection{AI Service Deployment}
The AI service, which handles resource-intensive tasks such as natural language processing and semantic search, is developed in Python. It requires a specific runtime environment with complex dependencies defined in \texttt{requirements.txt}. To ensure consistency across environments, it is containerized using Docker and deployed to Google Cloud Run.

\begin{itemize}
    \item \textbf{Containerization:} A \texttt{Dockerfile} is utilized to package the Python application, its system dependencies, and Python packages into a standardized Docker image.
    \item \textbf{Google Cloud Run:} Cloud Run is a fully managed compute platform that automatically scales stateless containers. It is chosen for the AI service because it can efficiently provision the necessary CPU and memory resources for inference requests and scales down to zero when idle, optimizing operational costs.
    \item \textbf{Deployment Process:} The Docker image is built and pushed to Google Artifact Registry. A Cloud Run service is then deployed referencing the uploaded image. The service is securely configured with necessary environment variables and allocated sufficient resources to handle concurrent AI workloads.
\end{itemize}

\subsubsection{System Integration}
The decoupled deployment architecture ensures that each service can scale independently based on its specific load. The frontend communicates with the Vercel-hosted Express backend via standard HTTPS RESTful APIs. The Express backend, in turn, forwards specialized AI requests to the Google Cloud Run endpoint, acting as an API gateway. This modular deployment strategy enhances fault tolerance, maintainability, and scalability.
